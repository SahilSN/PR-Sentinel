## Finding

### High: revert PR can overwrite a later human file after an autonomous rename

`run_guard` checks whether files changed after the autonomous merge before constructing a revert PR. For a renamed file, that check includes only the new `filename`, while `revert_entries` also restores the `previous_filename`.

Reproduction:

1. An autonomous merge renames `old.py` to `new.py`.
2. A later human commit creates a new `old.py` while leaving `new.py` unchanged.
3. Default-branch CI fails and the post-merge guard runs for the autonomous merge.
4. `changed_since` receives only `new.py` and reports no later change.
5. The generated revert tree deletes `new.py` and restores the pre-merge `old.py`, replacing the later human-created `old.py` in the proposed revert.

The configured guard opens a pull request rather than merging it, so a human review is still required. However, the revert is described as safe even though it can undo unrelated later work.

Recommended correction: include both `filename` and `previous_filename` in the changed-since safety check for renamed files, and add a regression test covering recreation or modification of the old path.

## Recommendation

**Core review and shadow-mode demo: ready. Autonomous merge mode: not ready.** Keep `SENTINEL_AUTONOMY` capped at `shadow` or `fix` until the rename-aware post-merge guard is repaired and the autonomous fix/merge/revert paths are live-tested on disposable pull requests.
